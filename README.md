# 顔マスク処理アプリケーション 基本仕様書

**最終更新：2026/09/10（現行コード確認済み）**

## 1. システム概要

ユーザーがアップロードした画像から顔領域を自動検出し、顔部分にマスク（スタンプ）を描画して表示するWebアプリケーション。

## 2. システム構成・役割分担

* **フロントエンド (Client Side / ブラウザ)**
    * 画面UIの表示（画像の選択、ドラッグ＆ドロップ領域、ボタン配置）
    * 選択された画像のプレビュー表示
    * Canvas APIを用いた顔領域へのマスク描画処理
* **バックエンド / API Route (Server Side / Node.js)**
    * フロントエンドから画像データを受信
    * 顔検知API（外部サーバー）へのプロキシ（中継）処理
    * 機密データ保護: APIキー（x-api-key）をサーバーサイドでのみ保持し、ブラウザ側に露出させない
    * リクエストの妥当性検証（サイズ・形式チェック）
* **顔検知サーバー (外部 API)**
    * 画像を受け取り、顔の位置座標データ（box）をJSON形式で返却
    * 複数人が写っている場合、検出された全ての顔の座標を配列で返却

## 4. 機能要件

### ① バックエンド (API Route: `/api/detect`)

* **エンドポイント:** `POST /api/detect`
* **入力:** `multipart/form-data`（画像ファイル、フィールド名`file`）
* **処理フロー:**
  1. ファイルの存在・型（Blob）チェック
  2. ファイルサイズチェック（上限10MB）
  3. MIMEタイプチェック（jpeg / png / webp のみ許可）
  4. 環境変数（`FACE_API_URL` / `FACE_API_KEY`）の存在チェック
  5. 外部顔検知APIへリクエストを中継（タイムアウト10秒）
  6. 外部APIのJSONレスポンスとステータスコードをブラウザへ返却
* **出力:** 正常時は外部APIの顔座標データ（JSON）。アプリ内で検出したエラーは`{ error: "..." }`形式
* **現状の制約:** 外部APIの応答内容はバックエンドでは検証・整形していない。JSONとして解析できない応答や通信例外は、共通の500エラーになる

### ② フロントエンド (`app/page.tsx`)

* **ファイル入力:** Drag & Drop およびファイル選択ダイアログ対応（`accept`属性で許可形式を明示）
* **入力バリデーション:** MIMEタイプ・ファイルサイズ（上限10MB）をアップロード時点でチェック
* **API通信:** プレビュー画面から`/api/detect`へ画像を送信し、`result`が配列であることを確認して座標を取得
* **サーバーエラーの表示:** `/api/detect`が返すエラー本文（`error`プロパティ）を読み取り、可能な限りそのままユーザーへ表示
* **多重送信防止:** `useRef`（`isRequestInFlight`）により、`isLoading`のstate更新を待たずに即座に多重リクエストをガード
* **マスク描画:** 取得した`x_min` / `y_min` / `x_max` / `y_max`の座標に基づき、Canvas API（`fillText`）で顔部分に絵文字スタンプ（😊）を描画
* **複数人対応:** 検出された全ての顔（`box`の配列）に対してマスクを描画

## 5. 非機能要件・エラー処理要件

### エラーハンドリング実装状況一覧

課題PDFの問い「このアプリにおいてどういうエラーが発生しそうか？」に対し、現行の`app/page.tsx`と`app/api/detect/route.ts`を確認した結果は以下の通り。

| No. | ケース | 対応状況 | 実装内容 |
| :-- | :-- | :-- | :-- |
| 1 | 非画像ファイル選択 | ✅ 実装済み | MIMEタイプで制限。`<input accept>`属性も実際の許可形式に合わせて表示 |
| 2 | 顔が検出されない | ✅ 実装済み | 「顔が検出されませんでした」を表示 |
| 3 | 通信自体の失敗 | ✅ 実装済み | `fetch`自体の失敗（ネットワーク切断等）を`catch`で捕捉し、他のエラーケースと区別して表示 |
| 4 | `/api/detect`がエラーレスポンスを返す | ✅ 実装済み | サーバーが返す`{ error: "..." }`本文を読み取り、具体的なメッセージをユーザーへ表示 |
| 5 | ファイル未送信（サーバー側） | ✅ 実装済み | 400エラーを返却 |
| 6 | 環境変数未設定 | ✅ 実装済み | 500エラーを返却 |
| 7 | 予期しないサーバー例外 | ✅ 実装済み | フロント側で`response.ok`の判定と`fetch`失敗（`catch`）を分離し、原因ごとに異なるメッセージを表示できる構造に変更 |
| 8 | ファイルサイズ超過 | ✅ 実装済み | フロント・バックエンド両方で10MB上限チェック |
| 9 | サーバー側の画像形式検証 | △ 一部実装 | MIMEタイプは検証済み。ただし、拡張子やMIMEタイプを偽装したファイルを見分けるバイナリ内容の検証は未実装 |
| 10 | 外部APIのタイムアウト | △ 一部実装 | `AbortSignal.timeout(10_000)`で10秒後に中断する処理は実装済み。タイムアウトを個別判定せず共通の500エラーを返すため、タイムアウト専用のステータス・メッセージは未実装 |
| 11 | 外部APIの不正レスポンス | △ 一部実装 | フロントで`data.result`が配列かを確認済み。ただし、各`box`の存在、座標値の型・範囲は未検証。外部APIがJSON以外を返した場合も共通の500エラーになる |
| 12 | 複数人の顔が検出された場合 | ✅ 実装済み | 全ての`box`に対しマスクを描画（`result[0]`のみの処理から変更済み） |
| 13 | ボタン連打（多重送信） | ✅ 実装済み | `disabled`によるUI制御に加え、`useRef`（`isRequestInFlight`）で再レンダリングを待たない確実なガードを実装 |
| 14 | 画像の破損・読み込み失敗 | △ 実装済み・未検証 | `<img>`の`onError`、Canvas描画用`Image()`の`onerror`を実装。実際の壊れた画像での動作確認は未実施 |

**進捗：14項目中10項目は実装済み、3項目（No.9〜11）は一部実装、1項目（No.14）は実装済み・未検証**

### 再試行案内について（要対応）

現状、エラー発生時のメッセージ表示は実装済み。ただし、**再試行を明示的に促す説明や専用ボタンは未実装**。プレビュー画面に残るケースでは「画像をマスク」ボタンを再度押せるが、ユーザーへの案内は表示されない。

### セキュリティ

* APIキーは`.env`（`.env.local`相当）で管理し、Gitにコミットしない（`.gitignore`で除外設定済み、`git check-ignore`で除外確認済み）
* APIキーはバックエンド（API Route）でのみ保持し、ブラウザ側のコード・ネットワークタブに露出しない構成
* ファイルサイズとMIMEタイプの検証をフロントエンドとバックエンドの両方で実施（フロントを経由しない直接アクセスへの基本対策）
* ファイルのバイナリ内容による画像判定は未実装
* APIキー露出と`.gitignore`の最終確認は未実施

### コンプライアンス

* マスク素材は、Unicode文字の絵文字（😊）をCanvas APIの`fillText`で描画している。実際の絵柄はOSやブラウザが選ぶフォントに依存するため、公開・商用利用時は使用環境の絵文字フォント条件を確認する
* アプリはNext.js、React、Tailwind CSSなどの依存パッケージを使用している。各パッケージのライセンス一覧作成と最終確認は未実施

## 6. 今後の対応予定

1. No.14（画像読み込み失敗）の動作検証：意図的に壊れたファイルを用意し、エラーハンドリングが正しく動くか確認する
2. No.9（画像形式検証）：ファイル先頭のシグネチャなどを使うバイナリ内容の検証を追加するか、課題の対象外とするか決定する
3. No.10（タイムアウト）：タイムアウトを他の例外と分け、例として504と専用メッセージを返す
4. No.11（不正レスポンス）：`result`内の各要素について`box`の有無と座標値の型・範囲を検証する
5. エラー表示時に再試行方法を明示する。必要であれば専用の再試行ボタンを追加する
6. 想定エラー14項目の通し動作テストを行い、表示内容と画面遷移を確認する
7. APIキーがブラウザ側に露出していないことと、`.gitignore`が正しく機能していることを再確認する
8. 依存パッケージと絵文字表示に関するライセンス条件を確認する

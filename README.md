# 顔マスク処理アプリケーション 基本仕様書

**最終更新：2026/09/11（複数画像一括アップロード機能の要件を追加）**

## 1. システム概要

ユーザーがアップロードした画像から顔領域を自動検出し、顔部分にマスク（スタンプ）を描画して表示するWebアプリケーション。

## 2. システム構成・役割分担

* **フロントエンド (Client Side / ブラウザ)**
    * 画面UIの表示（画像の選択、ドラッグ＆ドロップ領域、ボタン配置）
    * 選択された画像のプレビュー表示
    * Canvas APIを用いた顔領域へのマスク描画処理
* **バックエンド / API Route (Server Side / Node.js)**
    * フロントエンドから画像データを受信
    * 顔検知API（外部サーバー）へのプロキシ（中継）処理
    * 機密データ保護: APIキー（x-api-key）をサーバーサイドでのみ保持し、ブラウザ側に露出させない
    * リクエストの妥当性検証（サイズ・形式チェック）
* **顔検知サーバー (外部 API)**
    * 画像を受け取り、顔の位置座標データ（box）をJSON形式で返却
    * 複数人が写っている場合、検出された全ての顔の座標を配列で返却

## 3. 画面設計・UI遷移仕様（現行：単一画像）

| 画面名 | 構成要素 | アクション / 遷移 |
| :--- | :--- | :--- |
| **1. 画像アップロード画面** | ・D&D対応ドロップエリア（クリックでもファイル選択ダイアログを起動）<br>・「画像を削除」「画像を送信」ボタン（現状は非活性表示。実際の遷移はドロップ/選択で自動発生） | ・画像をドロップ/選択 ➔ バリデーション通過後、**画面2**へ自動遷移 |

## 4. 機能要件

### ① バックエンド (API Route: `/api/detect`)

* **エンドポイント:** `POST /api/detect`
* **入力:** `multipart/form-data`（画像ファイル、フィールド名`file`）
* **処理フロー:**
  1. ファイルの存在・型（Blob）チェック
  2. ファイルサイズチェック（上限10MB）
  3. MIMEタイプチェック（jpeg / png / webp のみ許可）
  4. 環境変数（`FACE_API_URL` / `FACE_API_KEY`）の存在チェック
  5. 外部顔検知APIへリクエストを中継（タイムアウト10秒）
  6. 外部APIのJSONレスポンスとステータスコードをブラウザへ返却
* **出力:** 正常時は外部APIの顔座標データ（JSON）。アプリ内で検出したエラーは`{ error: "..." }`形式
* **現状の制約:** 外部APIの応答内容はバックエンドでは検証・整形していない。JSONとして解析できない応答や通信例外は、共通の500エラーになる

### ② フロントエンド (`app/page.tsx`)

* **ファイル入力:** Drag & Drop およびファイル選択ダイアログ対応（`accept`属性で許可形式を明示）
* **入力バリデーション:** MIMEタイプ・ファイルサイズ（上限10MB）をアップロード時点でチェック
* **API通信:** プレビュー画面から`/api/detect`へ画像を送信し、`result`が配列であることを確認して座標を取得
* **サーバーエラーの表示:** `/api/detect`が返すエラー本文（`error`プロパティ）を読み取り、可能な限りそのままユーザーへ表示
* **多重送信防止:** `useRef`（`isRequestInFlight`）により、`isLoading`のstate更新を待たずに即座に多重リクエストをガード
* **マスク描画:** 取得した`x_min` / `y_min` / `x_max` / `y_max`の座標に基づき、Canvas API（`fillText`）で顔部分に絵文字スタンプ（😊）を描画
* **複数人対応:** 検出された全ての顔（`box`の配列）に対してマスクを描画

| 2 | 顔が検出されない | ✅ 実装済み | 「顔が検出されませんでした」を表示 |

### 再試行案内について（要対応）

現状、エラー発生時のメッセージ表示は実装済み。ただし、**再試行を明示的に促す説明や専用ボタンは未実装**。プレビュー画面に残るケースでは「画像をマスク」ボタンを再度押せるが、ユーザーへの案内は表示されない。

### セキュリティ

* APIキーは`.env`（`.env.local`相当）で管理し、Gitにコミットしない（`.gitignore`で除外設定済み、`git check-ignore`で除外確認済み）
* APIキーはバックエンド（API Route）でのみ保持し、ブラウザ側のコード・ネットワークタブに露出しない構成
* ファイルサイズとMIMEタイプの検証をフロントエンドとバックエンドの両方で実施（フロントを経由しない直接アクセスへの基本対策）
* ファイルのバイナリ内容による画像判定は未実装
* APIキー露出と`.gitignore`の最終確認は未実施

### コンプライアンス

* マスク素材は、Unicode文字の絵文字（😊）をCanvas APIの`fillText`で描画している。実際の絵柄はOSやブラウザが選ぶフォントに依存するため、公開・商用利用時は使用環境の絵文字フォント条件を確認する
* アプリはNext.js、React、Tailwind CSSなどの依存パッケージを使用している。各パッケージのライセンス一覧作成と最終確認は未実施

## 8. 追加機能：複数画像一括アップロード（要件定義のみ・未実装）

> このセクションはお題「複数画像の一括アップロード — まとめて投入し、順に処理して一覧表示」に基づく新機能の要件定義であり、**現行コードにはまだ反映されていない**。実装時はこのセクションを実装内容に合わせて随時更新すること。

### 8.1 概要

複数の画像（最大10枚）をまとめて選択し、**プレビュー画面では矢印によるスライドショー表示**で内容を確認、一括でマスク処理を実行した後、**結果画面ではグリッド状の一覧表示**で全ての処理結果を見渡せる機能。既存の単一画像フローを置き換える形で実装する。

### 8.2 表示方式の使い分け（用語の整理）

| 用語 | 定義 | 本機能での適用画面 |
| :-- | :-- | :-- |
| スライドショー表示（カルーセル） | 画面には1枚だけ表示し、矢印で1枚ずつ切り替える | プレビュー画面 |
| 一覧表示（グリッド／サムネイル） | 複数の画像を同時に並べて表示する | 結果画面 |

### 8.3 処理フロー

1. **アップロード画面**：複数枚選択（先頭10枚を採用、11枚目以降は除外しエラー表示）
2. **プレビュー画面（スライドショー表示）**：矢印で各画像を1枚ずつ確認する（この時点ではAPI送信しない、閲覧のみ）
3. **「画像をマスク」ボタン押下**：選択された全画像を一括で`/api/detect`へ送信する。進捗を「処理中...（3/10枚完了）」の形式で表示する
4. **結果画面（一覧表示）**：全画像の処理結果をグリッド状に同時表示する。矢印ナビゲーションはこの画面では使用しない

### 8.4 画面構成

| 画面 | 表示方式 | 内容 |
| :-- | :-- | :-- |
| 1. アップロード画面 | - | 複数選択（先頭10枚採用、超過分はエラー表示） |
| 2. プレビュー画面 | スライドショー表示 | 1枚ずつ表示。左右矢印＋「N枚中M番目」で切り替え（閲覧のみ、未処理） |
| 3. 結果画面 | 一覧表示（グリッド） | 処理済みの全画像をサムネイル状に並べて同時表示。矢印なし |

### 8.5 プレビュー画面（スライドショー表示）の仕様

* 1枚目を表示中：左矢印を非表示
* 最後の1枚（N枚中N番目）を表示中：右矢印を非表示
* 中間の画像：左右両方の矢印を表示
* 「N枚中M番目」のカウンター表示を矢印付近に配置

### 8.6 結果画面（一覧表示）の仕様

* 処理が完了した全画像を、グリッドレイアウト（列数は実装時に決定）で並べて表示する
* 各枠には、マスク処理済みの画像（Canvas描画結果）を表示する
* エラーになった画像は、その枠内に個別のエラーメッセージ（例：「顔が検出されませんでした」）を表示し、一覧の中の1枠として扱う（他の画像の表示・処理には影響しない）
* 「戻る」ボタンでプレビュー画面（スライドショー表示）へ戻る
* サムネイルのクリックによる拡大表示・詳細表示は本要件のスコープ外（8.10参照）

### 8.7 データ構造（設計方針）

```typescript
type ImageItem = {
  file: File;
  previewUrl: string;
  boxes: Box[] | null;       // 未処理: null／処理済み: Box[]（顔なしなら空配列）
  itemError: string | null;  // この画像固有のエラーメッセージ（顔未検出・個別APIエラー等）
};

// Homeコンポーネントのstate（変更イメージ）
images: ImageItem[]
previewIndex: number          // プレビュー画面（スライド）での現在位置
isBatchProcessing: boolean    // 一括処理中かどうか
processedCount: number        // 進捗表示用（何枚完了したか）
uploadError: string | null    // 「11枚目以降は除外されました」等、アップロード時点の全体エラー
```

現行の単数管理（`file`, `previewUrl`, `boxes`, `apiError`等）は、上記の配列ベース構造に置き換える。

### 8.8 一括処理のロジック方針

* 各画像に対して`/api/detect`を呼び出す。`Promise.allSettled`で並行実行し、1枚の失敗が他の画像の処理を止めないようにする
* 各画像の結果は個別に`ImageItem.boxes`または`itemError`に格納する
* 各Promiseの完了ごとに`processedCount`を更新し、進捗表示に反映する
* 全件の処理完了後に結果画面へ遷移する

### 8.9 既存エラーハンドリング（14項目）との対応

| No. | ケース | 複数画像対応での扱い |
| :-- | :-- | :-- |
| 2・4・11 | 顔未検出／APIエラー／不正レスポンス | 画像単位で`itemError`にセットし、結果一覧の該当枠に表示。処理全体は継続 |
| 3・7 | 通信失敗／予期しないサーバー例外 | 個別画像の通信が失敗した場合もその画像だけエラー扱いとし、全体は継続 |
| 8・9 | サイズ超過／形式不正 | アップロード画面の時点で画像ごとに事前チェックし、条件を満たさない画像は選択の時点で弾く |
| 13 | ボタン連打（多重送信） | 「画像をマスク」ボタン自体の連打防止のみで良い（`useRef`は1つ、画像枚数分は不要） |
| 14 | 画像読み込み失敗 | 画像ごとの`<img>` `onError`はそのまま個別対応 |

### 8.10 アップロード枚数の制限

* 上限：**10枚**
* 11枚以上選択された場合：先頭10枚を採用し、11枚目以降は除外する。除外があった場合は`uploadError`にメッセージ（例：「最大10枚までです。〇枚が選択から除外されました」）をセットして表示する。有効な先頭10枚の処理はそのまま進める

### 8.11 スコープ外（本要件では対応しない）

* 全画像の一括ダウンロード・一括保存
* 画像の並び替え
* グリッド内サムネイルのクリックによる拡大表示・詳細表示
* アップロード後の画像追加・個別削除（既存の「画像を削除」ボタンの複数枚対応版の仕様は別途検討）

### 8.12 実装時の未決定事項

* 結果画面グリッドの列数・レスポンシブ対応の詳細デザイン
* `Promise.allSettled`による並行送信数に上限を設けるか（外部APIのレート制限次第で検討）
* 「画像を削除」ボタンの複数枚モードでの挙動（現在表示中の1枚のみ削除か、全体削除か）は未確定
